# B5.5 — "on my way" by voice and SMS keyword: design (Fable-authored)

Decision F-3 (Part F, RECORDED): both new legs invoke the **same audited direct status act** as
the shipped app button — not a proposal. No new `JobStatus` value.

## What already exists (verified, reuse verbatim)

`POST /api/dispatch/appointments/:id/en-route` (`packages/api/src/dispatch/routes.ts:262-317`)
already does, in order: appointment lookup → **technician speaker-scoping** (a technician actor
must appear in `assignmentRepo.findByAppointment`, else 403) → `enRouteCoordinator
.enqueueEnRouteNotice({tenantId, appointmentId, technicianName})` → `emitEnRouteAudit` →
202 with the coordinator's `idempotencyKey`. The coordinator
(`notifications/delay-notifications.ts:419-498`) renders the branded ETA SMS
(`renderEnRouteTemplate`), is DNC-suppressed, and returns `null` when no recipient resolves.

**The idempotency key returned by the coordinator is the mechanism AC-4 needs** — a second
utterance inside the window must not double-text. Verify how the key dedups before asserting on
it; do not invent a second dedup layer.

## Voice leg

- **Intent** `en_route` added to `SUPPORTED_INTENTS`. **Deliberately NOT in
  `INTENT_TO_PROPOSAL_TYPE`** — instead registered in the documented **non-proposal set**, the
  same way `lookup_*` is (`proposals/voice-intent-map.ts:48-52` explains that convention), so
  B7.11's drift test reads its absence as intentional rather than as a gap. Catalog doc
  `docs/reference/voice-action-catalog.md` updated in the same commit; both contract tests green.
- **Confidence floor (the classification-risk mitigation F-3 promises):** a low-confidence
  `en_route` classification MUST gate to clarification rather than fire. Pin with a test at the
  routing site.
- **Speaker scoping (AC-2):** resolution queries the acting user's OWN assignments only. A
  technician's "on my way" can never target another tech's appointment. The unit test asserts the
  query is filtered by the acting user — assert on the filter, not just the outcome, so a future
  refactor that widens the query fails the test.
- **Resolution (AC-3):** named job → that appointment; bare "on my way" → the tech's next
  upcoming appointment **today**; two candidates → clarification; zero → an explicit
  spoken/visible "no upcoming appointment" outcome, asserted — never silent.

## SMS leg (AC-5)

`OMW` / "on my way" join `TECH_STATUS_KEYWORDS`
(`packages/shared/src/contracts/tech-status-event.ts:70`, currently `['out','sick','unavailable']`).
Note the shape difference: the existing three are **availability statuses**; en-route is an
**act**. Keep `TECH_STATUS_VALUES` (the status enum, line 31) unchanged and only extend the
keyword set + its dispatcher, so no new status value leaks into the status domain. Handler-suite
tests cover: keyword match from a registered tech phone, non-tech sender ignored, DNC/consent
invariants untouched.

## Integration proof (AC-4)

`test/integration/en-route-voice.test.ts` (real Postgres): voice-triggered en-route →
`appointment.en_route_triggered` audit with the **tech** actor + a customer ETA SMS dispatch row
from the existing branded template; idempotence (second utterance in-window sends nothing more);
cross-tenant negative.
