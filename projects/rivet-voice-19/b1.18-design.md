# B1.18 — brand voice by voice, lock stays tap-only: design (Fable-authored)

Smallest honest scope: **one new intent + one new proposal type**. No multi-turn interview.
Capture is speakable; **lock is not** (Part F entry F-2; same theory as D-013).

## Why this is cheap to get right and expensive to get wrong

The versioned write path already exists and is TOCTOU-safe: `updateBrandVoice`
(`packages/api/src/tenants/brand/brand-voice-service.ts:40-91`) does read → cool-down check →
merge → version bump **atomically under the repo's row lock** (`bumpVersion`), throws
`BrandVoiceCooldownError`, and returns the `brand_voice.updated` audit event for the caller to
persist. The execution handler MUST call this function — not re-implement any of it. Re-implementing
the merge or the cooldown is the expensive mistake this design exists to prevent.

## Contract (AC-1)

- **Intent** `update_brand_voice` → `SUPPORTED_INTENTS` (`ai/orchestration/intent-classifier.ts`).
- **Proposal type** `update_brand_voice` → `INTENT_TO_PROPOSAL_TYPE`
  (`proposals/voice-intent-map.ts`) + `ProposalType` union (`proposals/proposal.ts`).
- **Zod payload** in `proposals/contracts.ts`, mirroring the six fields exactly as
  `brandVoiceSchema` defines them (`tenants/brand/brand-voice.ts:31-38`) — reuse that schema
  rather than restating the field list, so a future field addition can't drift:
  `register` ('formal'|'friendly'|'casual'), `opening_lines` (≤5 × ≤200 chars), `signoff` (≤200),
  `banned_phrases` (≤50 × ≤200), `persona_name` (≤120), `pronoun` ('we'|'i'), plus an optional
  `freeText` field for unmapped instructions (AC-2: nothing spoken is dropped).
- **Action class**: add to `actionClassForProposalType` (`proposals/proposal.ts:282-418`) as
  **`manual`** — NOT capture. `capture` is auto-approvable at high confidence under an autonomous
  tier; brand voice is the tenant's locked outbound identity and a wrong extraction poisons every
  outbound message. AC-1 demands an assertion that `decideInitialStatus` can never auto-approve
  this type at any trust tier; `manual` makes that structural rather than threshold-dependent.
- **Execution handler** registered with `isFullyWired()` returning `Boolean(brandVoiceRepo)`;
  never a synthetic-id passthrough (WS3 convention — see `AddNoteExecutionHandler`).
- Catalog doc `docs/reference/voice-action-catalog.md` + launch fixtures updated in the SAME
  commit; both intent-map contract tests green (Guardrail 4).

## Execution (AC-3)

Handler calls `updateBrandVoice({ actor: {tenantId, userId: context.executedBy, role}, patch })`
with `onboarding: false` (a spoken edit is a normal edit, cool-down applies), then persists the
returned audit event via the audit repo. A `BrandVoiceCooldownError` surfaces as an **honest
failed-execution reason** on the proposal (`{ success: false, error: 'brand_voice_cooldown: …' }`)
— never a silent skip, never a success with nothing written.

## The lock negative (AC-4)

The payload has **no field capable of expressing lock**, so "lock my brand voice" cannot set
`brand_voice_locked` even if it classifies as this intent. Test both admissible outcomes: it maps
to the capture intent (whose payload can't lock) or it clarifies. Log which one the classifier
actually does.
