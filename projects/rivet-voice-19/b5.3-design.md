# B5.3 — assign work by speaking: design (Fable-authored)

Three defects stack here. Fix them independently; only the third is delicate.

## 1 · The unconditional gate (mechanical)

`ReassignAppointmentTaskHandler` (`ai/tasks/voice-extended-tasks.ts:377-378`) pushes
`appointmentId` into `missingFields` unconditionally, ignoring the id the router already resolved
and threaded onto `existingEntities.appointmentId` (`workers/voice-action-router.ts:1498-1500`).
Fix: read the threaded id first — exactly the shape `RescheduleAppointmentTaskHandler` already
uses at :330-339 (resolved id → payload; free-text reference → carry the reference AND gate;
nothing → gate). Do not invent a new pattern; copy the sibling's.

## 2 · The classifier minimal pair (test-decided, not luck)

"Assign Carlos to the Johnson job" must classify `reassign_appointment`, while "Add Carlos to the
Garcia appointment" must stay `add_crew_member` — reassign REPLACES the primary tech, add_crew
ATTACHES a non-primary one. Three launch fixtures pin it (AC-1), including "Put Carlos on the
Garcia job instead of me" → `reassign_appointment`. The prompt/few-shot work belongs with the
fixtures in the same commit.

## 3 · The resolver fallback — the delicate one. READ THIS BEFORE EDITING.

`resolveAppointment` (`ai/resolution/pg-entity-resolver.ts:252-269`) falls to
`resolveUpcomingAppointment` (:397-437) when the reference is neither a parseable date phrase nor
job-anchored. That fallback is **tenant-wide, soonest-first**, and returns `resolved` when
exactly one upcoming appointment exists.

**It is not simply wrong.** For a genuinely NAMELESS reference — "cancel the upcoming
appointment", the SCH-03 single-turn cancel case its docstring describes — returning the tenant's
only upcoming appointment is a reasonable resolution, and the tri-state (1 → resolved, 2-5 →
ambiguous, 0 or >5 → not_found) already refuses to guess when there is real ambiguity. **Do not
delete this fallback.** Deleting it re-breaks SCH-03: every first-turn "cancel the upcoming
appointment" escalates to on-call again.

**What IS wrong** is the named case. "the Johnson job" carries a name. If no job matches
"Johnson", the name is silently discarded and the caller gets whatever appointment happens to be
next — an answer about a different customer entirely. The user said a name; the system answered
about someone else. That is the AC-3 defect.

**The fix, stated precisely:** when the reference contains a name-like token that was searched
and matched nothing, return `not_found` (or `ambiguous` where candidates exist) — never fall
through to the nameless tenant-wide branch. When the reference carries no name-like token at all,
the existing fallback stands unchanged.

Pin BOTH sides with `pg-entity-resolver` unit tests (real Postgres — this resolver's Pool was
mocked once before and shipped nonexistent column names; per CLAUDE.md, mocked-DB coverage is not
proof here):
- a non-matching NAMED reference yields `not_found`/`ambiguous`, never a fallback id — even when
  the tenant has exactly one upcoming appointment (the case that would otherwise "resolve");
- a NAMELESS reference with exactly one upcoming appointment still resolves (SCH-03 unbroken).

## 4 · Job-name → appointment resolution (AC-3 positive path)

"the Johnson job" resolves job → appointment: unique upcoming appointment for that job → its id
lands on the payload; multiple → `voice_clarification` with ≤5 candidates carrying **date +
assigned tech** (so the picker is answerable). `resolveAppointmentByJob` (:320-362) is the
existing job-anchored query to build on.
