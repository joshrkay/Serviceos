# B8.10 — estimate nudge by voice: design (Fable-authored)

"Nudge the Khan estimate" is blocked by a *design comment*, not a missing capability:
`SendEstimateNudgeTaskHandler` (`ai/tasks/voice-extended-tasks.ts:656-677`) hard-codes
`missing = ['estimateId']` because the customer/job entity resolver never resolved estimates. The
resolution technique already exists elsewhere.

## Reuse, don't invent

`EstimateEditTaskHandler.resolveEstimateIdGate` (`ai/tasks/estimate-edit-task.ts:427-461`) is the
proven pattern. Note its two-part behavior and copy the *verification* half exactly:

- an id-shaped `estimateReference` is **verified against the repo** before being trusted
  (`:441-443` — never trust an LLM-shaped UUID);
- a free-text match stamps `payload.estimateId` for review-card context but **still gates**.

B8.10 deliberately goes one step further than that second half: a *unique, verified, nudgeable*
match lifts the gate (that is the whole point of the item). The verification requirement does
not relax.

## Nudgeable states (AC-3)

Only `sent` / `viewed` participate in matching. Not `draft` (nothing was ever sent, so there is
nothing to nudge), not `accepted` / `declined` (decided), not `expired`.

**Decision (logged, per AC-3): a unique match in a NON-nudgeable state gates with a reason
surfaced on the draft — it does not become a clarification.** Rationale: clarification asks the
owner to pick among candidates, but here there is no ambiguity to resolve — the estimate is
simply not nudgeable. Saying "the Khan estimate was already accepted" is a better answer than
offering a picker with one disabled row.

## Ambiguity (AC-2)

Two nudgeable Khan estimates → `voice_clarification` with candidates carrying **estimate number +
amount + age**, so the picker is answerable by ear.

## The cooldown is the interesting proof (AC-5)

`ESTIMATE_NUDGE_COOLDOWN_MS = 48h` lives at `proposals/execution/handlers.ts:1008`, enforced at
`:1068` against a cooldown floor. The AC requires proving it **holds under voice**: a second
voice-approved nudge inside the window sends nothing and **records the suppressed outcome**.

Extend `test/integration/estimate-nudge.test.ts` (already 7 tests, real Postgres, claim-before-send
semantics — read them first; the file understands this domain better than a new file would). Add:
1. voice-produced payload (from the REAL task handler, not hand-built) → approve → execute →
   dispatch row + audit event;
2. a second voice-approved nudge inside 48h → no send, suppressed outcome recorded;
3. cross-tenant negative.
