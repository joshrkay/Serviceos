# Rivet / "AI Service OS" — Backend Feature Inventory (`packages/api`)

Authoritative route list: `packages/api/test/app/__snapshots__/route-manifest.test.ts.snap` (123 layers, 85 mounted routers, exposure classes `authenticated` / `webhook` / `public-token` / `open`), generated by `packages/api/src/app-route-manifest.ts`. Composition root is `packages/api/src/app.ts` (~7,000 lines). `packages/api/CONTEXT.md` is a **voice glossary only** — it defines Surface / Transport / Actor / Proposal-first (D-004) / Coverage table, not a feature list.

Status legend: **shipped** = wired in `app.ts` and reachable; **env-gated** = shipped but no-ops/503s without a credential or env flag; **partial** = one half of the loop exists; **dormant** = code exists with no production caller.

Note on feature flags: the only *named* flag in the flag store used at runtime is `force_primary_provider` (`ai/gateway`). Everything else is gated by **env vars** or **per-tenant `tenant_settings` booleans**, not by `flags/feature-flags.ts`. The flag admin API (`/api/admin/feature-flags`, Pg-persisted, platform-admin gated) is shipped but essentially unused by product code.

## Notable gaps I noticed (things a field-service product usually has that I could not find)

**Money**
- **No tax engine.** There is no tax-rate table, no jurisdiction-based sales-tax lookup, no Avalara/TaxJar integration. Tax exists only as a per-document bps field carried through the billing engine and the tax *export*. No exempt-customer handling, no per-line taxability.
- **No double-entry ledger / GL.** `RIVET_MONEY_EXTRACTION_FINDINGS.md` and `money-reconciliation.ts` confirm invoice balances are stateful counters with no ledger behind them; the reconciler detects drift rather than preventing it.
- **No credit memos or write-offs as first-class documents** (service credits are a goodwill ledger, not an AR instrument).
- **No purchase orders, vendor records, or supplier catalog.** Materials are a shopping list; there is no PO, no vendor bill, no cost-of-goods pipeline from a supplier.
- **No inventory / truck stock / parts on hand.** Catalog items have prices but no quantities, no warehouse or vehicle stock, no reorder points.
- **No payroll, commissions, or bonus calculation** on time entries. Time tracking has no pay rates, no overtime rules, no approval workflow, and no export to a payroll provider.
- **No ACH / bank transfer / Plaid.** Card-only via Stripe (+ Terminal card-present).
- **No multi-currency.** Integer USD cents throughout.
- **No customer statements** (an aged AR statement per customer) or aging report beyond the dashboard's outstanding/overdue snapshot.
- **No change-order approval surface** — `create_change_order` is a proposal type, but there is no customer-facing change-order approval page equivalent to the public estimate flow.

**Scheduling / dispatch**
- **No route optimization.** Travel time exists per-pair, but nothing sequences a technician's day or solves a multi-stop route.
- **No drive-time-aware auto-dispatch / auto-assign** beyond feasibility checking of a *proposed* tech.
- **No arrival-window / ETA product** and no customer-facing technician tracking, despite GPS ping ingestion.
- **No capacity planning or utilization forecasting.**
- **No job templates with checklists attached at schedule time** (job forms are attached per submission, not preloaded from a job type).

**Customer-facing**
- **No e-signature.** Estimate approval captures IP + UA for non-repudiation but there is no drawn/typed signature capture, and no signature on job completion / work order sign-off.
- **No customer-facing quote comparison ("good / better / best" option selection)** on the public estimate page — bundles exist internally but the approval flow is single-option accept/decline.
- **No portal self-serve invoice dispute or partial-payment selection.**

**Comms / marketing**
- **No email templates with a designer/WYSIWYG**, no campaign scheduling, no A/B tests, and **no open/click tracking** (the SendGrid event webhook is a no-op).
- **No postcards / direct mail** (Jobber ships this alongside email campaigns).
- **No 10DLC / A2P brand-and-campaign registration workflow** — per-tenant Twilio numbers are provisioned, but nothing models messaging-service registration status, which US SMS at scale requires.
- **No review platform beyond Google.** `yelpReviewUrl` is a link only; there is no Facebook/Yelp/Angi review ingestion.

**Reporting**
- **No scheduled/emailed report delivery** and no custom report builder — reports are fixed endpoints.
- **No audit-log read API** despite an `audit:view` permission existing in RBAC.

**Platform**
- **Only three roles** (owner / dispatcher / technician) with a frozen permission matrix — no custom roles, no per-permission role editing, no CSR/office-manager/sales role.
- **No public/partner API** — no API keys, no outbound webhooks *to* tenants (`webhooks/` is inbound-only), no Zapier surface. The OpenAPI spec advertises a `/api/v1` base that is not mounted.
- **No import/export of customers or jobs** (no CSV importer, no bulk data migration path off a competitor).
- **i18n covers EN + ES only**, and only for notifications/voice — there is no localization of the API's own error copy or of estimate/invoice document templates.
- **No equipment / asset registry per service location** (serial numbers, install dates, warranty expiry) — a standard HVAC/plumbing expectation that maintenance contracts would normally hang off.
- **No warranty tracking or callback/rework classification.**
