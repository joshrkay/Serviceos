- Judgment call: tenant B's half of this proof is driven directly against
  `/api/public/booking/:tenantId` (the same product surface the browser page
  itself calls) rather than through a second full browser page load. Two
  reasons, both discovered while iterating this spec, documented rather than
  silently worked around: (1) `/api/public/booking` is rate-limited to 5
  req/min per IP (packages/api/src/app.ts:3053-3078), and tenant A's own page
  load already costs 2 GETs — React 18 StrictMode double-invokes the
  availability-fetch effect on mount in dev — plus 1 POST, leaving no budget
  for a second full page load in the same window; (2) an attempt to wait out
  the rate-limit window (`page.waitForTimeout(65_000)`) surfaced a real,
  pre-existing defect instead: the API process crashed on an uncaught
  "terminating connection due to idle-in-transaction timeout" from its
  `dropped-call-worker` sweep (`dropped-call sweep: send-batch fetch failed`,
  `Cannot use a pool after calling end on the pool`), unrelated to this
  story and out of scope to fix here (no product code changes). Tenant A's
  full flow — the story's actual named surface — is still proven end to end
  through the real browser; tenant B's slots/isolation are proven through the
  identical backend path with no SQL, no platform-admin route, and no faked
  response.
- Incidental finding, not fixed (out of scope, no product code changes): the
  `dropped-call-worker` sweep's DB transaction can go idle-in-transaction and
  crash the whole API process on an uncaught exception rather than failing
  its own sweep gracefully. Reproduced twice by simply letting the dev
  webServer run for ~1.5-2 minutes; harmless to this spec's own assertions
  (the crash always landed after the test's own requests had already
  completed) but worth a ticket.
